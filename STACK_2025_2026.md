# Titan Voxel Engine — Stack actualizado (2025–2026)

Este documento toma como base el [ANALISIS_PROYECTO.md](./ANALISIS_PROYECTO.md) y describe **cómo usar los mismos lenguajes y componentes del proyecto (Rust, GLSL, Lua) con tecnología y actualizaciones de finales de 2025 y 2026**. Incluye versiones recomendadas, alternativas modernas y guía de migración.

---

## 1. Resumen del stack actual vs. stack 2025–2026

| Componente | En el proyecto actual | Recomendación 2025–2026 |
|------------|------------------------|---------------------------|
| **Lenguaje base** | Rust, edición 2021 | Rust, **edición 2024** |
| **Gráficos / ventana** | Ninguno (solo CPU) | **wgpu** + **winit** |

| **Paralelismo** | rayon declarado, no usado | **rayon** para meshing multichunk |

## 2. Rust: edición 2024 y ecosistema 2025–2026

### 2.1 Edición 2024

- **Cargo.toml**: usar `edition = "2024"` (por defecto en proyectos nuevos con Rust estable reciente).
- **Resolver**: la edición 2024 implica `resolver = "3"` y resolución consciente de `package.rust-version`.
- **Nombres en Cargo.toml**: preferir guiones: `default-features`, `dev-dependencies`, etc. (el comando `cargo fix --edition` ayuda a migrar).

Ejemplo de `Cargo.toml` actualizado:

```toml
[package]
name = "titan_voxel_engine"
version = "0.3.0"
edition = "2024"
rust-version = "1.84"

[dependencies]
glam = "0.30"
rayon = "1.10"
wgpu = "28"
winit = "0.30"
mlua = { version = "0.11", features = ["lua54"] }
# bitflags solo si se usan; si no, eliminar
```

### 2.2 Dependencias recomendadas para el motor

- **glam**: actualizar a **0.30.x** (mejoras de rendimiento y API; compatible con el uso actual de `IVec3` y vectores).
- **wgpu**: **v28** (diciembre 2024); soporta mesh shaders, múltiples backends (Vulkan, Metal, D3D12, GL), y WebGPU/Web. MSRV típico ~1.93.
- **winit**: **0.30.x**; modelo basado en `ApplicationHandler` y `EventLoop::run_app()`; soporte multiplataforma (Windows, macOS, Linux, Web, iOS, Android).
- **rayon**: **1.10+**; usar para paralelizar generación de mallas de varios chunks (`par_iter` sobre chunks).
- **mlua**: **0.11+**; soporta Lua 5.4, 5.5, LuaJIT y Luau; API segura, traits `FromLua`/`IntoLua`; opcional async.

## 3. Gráficos: wgpu y shaders (2025–2026)

### 3.1 API gráfica: wgpu

- **wgpu** es la opción natural en Rust para un motor voxel multiplataforma: mismo código para Vulkan, Metal, D3D12, OpenGL y Web (WebGPU).
- **Versión reciente**: v28 (mesh shaders en Vulkan y passthrough en Metal/DX12).
- Para Titan Voxel Engine: no es obligatorio usar mesh shaders al inicio; el flujo actual (vertex + fragment) se mapea bien a un pipeline estándar de wgpu.

Flujo típico:

1. **winit**: crear ventana y event loop.
2. **wgpu**: `Instance` → `Adapter` → `Device` + `Queue`; crear `Buffer` para vértices/índices, `Texture` (array) para bloques, `RenderPipeline` con shaders WGSL (o GLSL vía naga).
3. En cada frame: actualizar buffers si el chunk cambió, bind texture array, draw indexed.

### 3.2 Lenguaje de shaders: WGSL (y GLSL vía naga)

- **WebGPU/WGSL** es el estándar que wgpu usa de forma nativa; la especificación WGSL sigue en evolución (W3C, actualizaciones 2025–2026).
- **Ventaja**: un solo shader en WGSL corre en escritorio y web sin cambios.
- **Texture arrays en WGSL**: se usan como `texture_2d_array` y `textureSample` con un índice de capa; equivalente conceptual a tu `sampler2DArray` en GLSL.

Ejemplo de fragment en WGSL (equivalente a tu `voxel.frag`):

```wgsl
@group(0) @binding(0) var u_TextureArray: texture_2d_array<f32>;

struct FragmentInput {
  @location(0) v_Uv: vec2<f32>,
  @location(1) v_Layer: u32,
};

@fragment
fn fs_main(in: FragmentInput) -> @location(0) vec4<f32> {
  let tex_color = textureLoad(u_TextureArray, vec2<i32>(i32(in.v_Uv.x * 16.0), i32(in.v_Uv.y * 16.0)), i32(in.v_Layer));
  if (tex_color.a < 0.1) { discard; }
  return tex_color;
}
```

- Si se quiere **mantener GLSL** (tus `.vert`/`.frag`): **naga** (incluido en wgpu) puede compilar GLSL a SPIR-V y wgpu consumirlo; en la práctica, migrar a WGSL suele simplificar el pipeline y aprovechar mejor las guías y ejemplos actuales (2025–2026).

### 3.3 Novedades WGSL/WebGPU (2025)

- Extensiones de **subgroup** (subgroup_id, subgroup_uniformity).
- **Uniform buffer** con layout estándar.
- **Texture component swizzle**, primitive index, mejoras en el compilador (Tint, análisis de rangos).
- Para un motor voxel clásico (vertex + fragment, texture array), el núcleo WGSL actual es suficiente; las extensiones son útiles para optimizaciones futuras.

## 4. Scripting: Lua y alternativas (2025–2026)

### 4.1 Lua 5.4 y 5.5

- **Lua 5.4** sigue siendo la versión estable más usada fuera de Roblox; **Lua 5.5** existe en el ecosistema (p. ej. lua-src-rs).
- **mlua 0.11+** soporta 5.4 y 5.5; permite cargar `scripts/init.lua`, leer la tabla de materiales y rellenar `TextureRegistry` desde Rust de forma segura.

Uso recomendado en Titan:

- Inicializar `Lua` con `mlua`, cargar `init.lua`.
- Leer la tabla de materiales (id, path, properties) y construir en Rust un `HashMap<u16, Material>` o alimentar `TextureRegistry`.
- Opcional: exponer funciones Rust al script (p. ej. “registrar bloque”, “obtener layer”) para que el contenido siga definido en Lua.

### 4.2 Luau (alternativa moderna)

- **Luau**: fork de Lua orientado a juegos (Roblox); JIT, anotaciones de tipos, mejoras de rendimiento.
- **mlua** tiene soporte experimental para Luau (luau-src-rs en el ecosistema mlua-rs).
- Para un motor voxel genérico, **Lua 5.4 + mlua** es la opción más directa y documentada; Luau tiene sentido si se prioriza máximo rendimiento en scripts o se targetea Roblox.

### 4.3 Resumen scripting

| Opción | Cuándo usarla |
|--------|----------------|
| **Lua 5.4 + mlua 0.11** | Integración estándar, datos de materiales y bloques desde `init.lua`. |
| **Lua 5.5 + mlua** | Si se quiere estar en la última rama estable de Lua. |
| **Luau + mlua** | Si se necesita JIT y tipos en scripts y se acepta dependencia Luau. |

## 5. Cómo aplicar este stack al proyecto actual

### 5.1 Orden sugerido

1. **Cargo**: pasar a `edition = "2024"`, actualizar `glam`, añadir `wgpu` y `winit`; quitar o usar `rayon` y `mlua`.
2. **Ventana**: implementar un bucle mínimo con winit (crear ventana, event loop); después crear dispositivo y cola wgpu a partir del surface de la ventana.
3. **Shaders**: reescribir `voxel.vert`/`voxel.frag` a **WGSL** (un `.wgsl` o dos, según prefieras) y crear el `RenderPipeline` con texture array.
4. **Buffers**: subir `mesh.vertices` e `mesh.indices` a buffers wgpu y dibujar; opcionalmente usar `TextureRegistry::get_layer_for_block` al construir la malla.
5. **Assets**: resolver rutas de shaders y texturas respecto al ejecutable o a una carpeta de assets (evitar depender del CWD).
6. **Lua**: integrar mlua, cargar `init.lua` y rellenar el registro de materiales/texturas; usar ese registro en el mesher y en la carga de la texture array.
7. **Paralelismo**: usar rayon para generar mallas de varios chunks en paralelo antes de subirlas a la GPU.

### 5.2 Rutas de assets (2025–2026)

- No usar solo CWD. Opciones:
  - `std::env::current_exe()` y luego `parent().join("shaders")` / `join("assets")`.
  - Crate **embed** para embeber shaders y/o listas de texturas en el binario (útil para releases).
  - Variable de entorno tipo `TITAN_ASSETS=/ruta/a/assets` para desarrollo.

### 5.3 Versiones de referencia (final 2025 – 2026)

- **Rust**: 1.84+ (edición 2024).
- **glam**: 0.30.x.
- **wgpu**: 28.x.
- **winit**: 0.30.x.
- **mlua**: 0.11.x (Lua 5.4 o 5.5).
- **rayon**: 1.10.x (si se usa paralelismo en meshing).
